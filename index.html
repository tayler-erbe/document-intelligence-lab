Five practice areas.

The studies group into the kinds of work I do: deciding which model to use, making it run fast enough, building the pipeline around it, designing the whole system, and advising on what is worth building at all.

Model evaluation

Fixed protocols, public benchmarks, failures counted, limits stated.

Performance engineering

Throughput, latency, GPU use and cost, measured at the load that matters.

Data engineering

Pipelines that turn documents into data a person can check.

Solution architecture

Model routes, hardware and orchestration chosen from evidence.

AI consulting

Trade-offs made plain, and a recommendation someone can act on.

02 / HOW THE LAB WORKS

What keeps the
results honest.

The newer studies follow these rules from the start. Older work is labelled where it differs.

01

Public data or design only

Private documents, extracted text and results from real-document runs stay on approved machines. What is published here is public-benchmark results, aggregates or design.

02

Method fixed before results

Prompts, scoring, thresholds and decision rules are written down before a run. Changing one means a new, labelled protocol.

03

Every attempt counts

Errors, timeouts and truncated outputs stay in the results as failures. Nothing is dropped to make a model look better.

04

Code checks, models point

Accuracy is scored by code against labels, not by another model. Where an older study used an AI reviewer, it says so.

05

Measured at real load

Speed is measured at the concurrency and document sizes the work will actually see, with GPU telemetry alongside.

06

Say what it does not show

A benchmark result is not real-document accuracy, and a prototype is not a production approval. Each page states which it is.
